# dependency-resolution-go

一套**确定性（deterministic）**的依赖版本解析库与命令行工具。多个模块各自声明依赖与
版本范围，本工具把这些声明合并成一张依赖图，求解出唯一、可复现、可解释的版本组合。

- **完全离线**：可用版本信息只来自本地注册表（内存索引、JSON 快照文件或本地目录树），
  全程不访问任何网络。
- **结果唯一**：相同输入下，无论模块声明顺序、并发程度还是进程是否重启，产出的版本
  组合与锁定文件逐字节一致。
- **可解释**：每个选定版本都记录了所有约束它的声明来源；冲突会给出矛盾区间、可用版本
  和全部矛盾来源。
- **多版本并存**：同一依赖的互不兼容大版本可在结果中各自存在，传递依赖不会跨大版本
  “串味”。
- **工作区**：多个成员各自持有清单并相互引用，跨成员统一求解；增删无关成员不改变
  其它成员的既有结论。
- **可复现安装**：一次求解固化为无时间戳、规范化序列化的锁定文件，并据其完成安装与
  校验。
- **增量求解**：清单小幅变化后重算受影响部分，增量结论与全量重算逐字段一致；取消或
  超时不会留下半成品锁定文件。

## 目录结构

| 包 | 职责 |
| --- | --- |
| `semver` | 语义化版本解析、优先级比较、版本范围（`^` `~` `>=` 通配 `||` 等）解析与匹配 |
| `manifest` | 依赖清单模型、JSON 读取、来源（Source）记录 |
| `registry` | 本地可用版本目录：内存 / JSON 索引 / 目录树三种实现 |
| `graph` | 把多处声明合并成一张带全部来源的依赖图，确定性遍历与环检测 |
| `compat` | 可配置的大版本兼容规则与 lane（并存大版本）切分 |
| `solver` | 确定性回溯 DFS 求解器、决策/拒绝记录、结构化失败 |
| `workspace` | 工作区成员、成员相互引用、成员对注册表的“影子化” |
| `lock` | 锁定文件规范化序列化、原子写、漂移校验、安装与核验 |
| `resolve` | 全量 / 增量编排、增量与全量一致性断言、原子提交 |
| `cmd/depresolve` | 离线命令行入口 |

## 版本范围语法

| 写法 | 含义 |
| --- | --- |
| `*` / 空 | 任意正式发布版本（不含预发布） |
| `1.2.3`、`=1.2.3` | 精确 |
| `^1.2.3` | 兼容更新：`>=1.2.3 <2.0.0`；`^0.2.x` 锁在 `0.2`；`^0.0.3` 仅 `0.0.3` |
| `~1.2.3` | 同 minor：`>=1.2.3 <1.3.0` |
| `>=1.0 <2.0` | 空格或逗号连接表示“且（AND）” |
| `1.x`、`1.2.*`、`1.2` | 通配区间（`1.2` 等价 `>=1.2.0 <1.3.0`） |
| `^1 || ^2` | `||` 表示“或（OR）” |
| `!=1.2.3` | 排除 |

预发布版本默认不参与匹配，仅当范围本身在**相同 major.minor 元组**上携带了预发布
比较器时才被接纳（与 npm/cargo 的常见心智一致），例如 `>=1.0.0-alpha` 可以接纳
`1.2.3-beta`，但 `>=1.0.0` 不会接纳任何预发布。

## 求解语义

### 1. 合并声明，全部成为依据

每个包的清单给出若干 `依赖@范围` 声明。同一个依赖被多处声明时（根、多个传递包、
多个工作区成员），这些声明**不会互相覆盖**，而是聚合到同一条图边上；求解时同一
lane 内必须同时满足所有区间，即取交集。每条声明都携带来源
（`kind / 成员 / 来源包 / 文件 / 原始范围文本`），因此任何结论或冲突都能追溯到
具体清单。

### 2. Lane：同一依赖的多个大版本并存

兼容规则把每个包的可用版本划分成若干 **lane**。默认规则是 `StrictMajor`：

- major ≥ 1：不同 major 是不同 lane（`1.x` 与 `2.x` 永不互相满足）；
- major = 0：默认把**每个 `0.minor` 视为破坏性版本**，`0.2.x` 与 `0.3.x` 分到
  不同 lane；
- 可按包覆盖规则，例如对某个包改用 `SameMajor`（让全部 `0.x` 共享一条 lane）。

声明按其区间被路由到 lane：

- **钉死 major 的区间**（`^1`、`~1.2`、`1.x`、精确版本等）只会进入对应 major 的
  lane；若两处钉到不同 major，就在结果中**并存**两条 lane，而不是冲突；
- **开放区间**（`>=1.0`、`*`）确定地附加到所有与之相交的既有 lane；若尚无 lane，
  则确定地选择**与之相交的最高 major** 建立 lane。

因此，传递依赖严格沿 lane 传播：选中的 `lib@2.x` 的依赖只会在 `lib#2` 这条 lane 的
求解中生效，绝不影响 `lib#1`。`compat.Rule.Explain` 给出某条声明能否落入某 lane 的
人类可读理由。

> 根上的开放区间（如 `>=1.0.0`）会**确定地落到最高 major**；若整条最高 lane 因传递
> 约束无解，求解按冲突失败，而不是静默把 major 降级——要锁在 1.x 应明确写 `^1`。
> 这保证结论唯一且可解释。

### 3. 确定性回溯绑定 + 快照回滚

求解器对每个 lane 维护一个“已尝试版本”集合，绑定过程采用 MRV（候选可行版本最少的
lane 优先，并列按 `包名, lane key`）递归展开，候选**从高到低**尝试。绑定某版本前对
可变状态（存在哪些 lane、各 lane 携带哪些声明）做快照；该版本传播出的子树一旦产生
矛盾（区间无交集、新开 lane 无任何可用版本、依赖本地缺失），就整体恢复快照并尝试更低
候选。可达的未绑定 lane 集合随绑定单调增量维护，避免在稠密图上重复全图遍历。由于不
依赖任何 goroutine 调度或 map 迭代顺序参与决策：

- lane 选择顺序：候选可行版本数最少的 lane 优先（MRV），并列时按
  `包名, lane key` 字典序；
- 每个 lane 的候选版本**从高到低**尝试；
- 选中一个版本后传播其发布清单里的依赖（可能创建新 lane），递归求解；
- 某候选导致矛盾（区间无交集、新开 lane 无任何可用版本、依赖包本地缺失）时，
  按深度回退并尝试更低版本；所有候选都失败时返回结构化冲突。

回滚通过对 lane 集合与各 lane 声明列表做快照 / 整体恢复实现，撤销精确、无共享状态污染。求解过程不使用任何 goroutine 或 map 迭代序参与决策，因此：

- 输入相同 ⇒ 选择相同（含每个 lane 的具体版本）；
- 与声明书写顺序、并发调用、进程重启无关。

可用版本集合、图声明与兼容配置共同参与一个 `InputsHash`（SHA-256），便于判断“输入
是否真的没变”。

求解受 `MaxSteps` 与 `MaxBacktracks` 预算保护，并全程响应 `context.Context`
取消 / 超时，规模较大时仍在可控资源内完成（见 `solver` 包的规模测试）。

### 4. 可区分的失败原因

所有失败都用 `solver.Failure` 表达，`Kind` 取值互斥且可程序判断：

| Kind | 触发情形 |
| --- | --- |
| `conflict` | 同一 lane 的区间交集无可用版本（附矛盾区间、可用版本、全部来源） |
| `cycle` | 依赖图出现环（附规范化后的环路径），直接失败、不死循环 |
| `missing_package` | 被依赖的包在本地注册表中没有任何版本（附要求方来源） |
| `missing_version` | 锁 / 安装要求的具体版本本地不存在 |
| `invalid_range` | 清单或发布元数据中的版本范围非法 |
| `invalid_version` | 版本号非法 |
| `canceled` | 上下文取消或超时 |
| `exhausted` | 超过求解步数 / 回溯预算 |

非法范围在**建图阶段**就被 `graph.InvalidRangeError` 拒绝；环检测分两处，确保任何
通过传递依赖形成的环都不漏报且不会死循环：

- **求解前**：对清单合并出的静态图做确定性三色 DFS；
- **求解后**：对“每个被选发布版本”的实际依赖边再做一次三色 DFS，捕获只在具体版本
  的发布元数据里出现的传递环（含自依赖）。

缺失依赖成为图节点并在求解时给出 `missing_package`。所有失败都在有界步数 / 回溯预算
内结束，不会 panic 或无限循环。

## 工作区语义

`workspace.New` 接收若干成员（`路径 → 提供的包名`），路径与包名都必须唯一。成员之间
互相引用时，引用范围在构造期被改写为“工作区合成版本”，保证成员**只解析到本地成员、
绝不解析到注册表同名发布版本**（成员影子化）。多个成员一起作为根求解，成员间共享的
外部依赖仍按上述 lane / 交集规则合并。新增或移除一个成员只影响它自己的子图，无关
成员的结论保持不变（有对应测试保障）。

## 锁定、漂移与安装

锁定文件是 JSON（`lockVersion: 1`），字段固定、无时间戳：units 与 reasons 排序后以
两空格缩进、无 HTML 转义方式序列化，重复序列化逐字节一致。`SaveFile` 采用
“同目录临时文件 + fsync + rename”原子提交，崩溃 / 取消都不会留下半个锁文件。

`lock.Verify` 把一次全新求解结果与锁文件比对，产出确定性排序的漂移列表：

- `missing`：求解需要、锁里没有；
- `extra`：锁里存在、已不再被需要；
- `changed`：同包同 lane 版本不一致。

处理策略 `lock.Policy`：

- `PolicyFail`：任何漂移都失败，旧锁保持不变；
- `PolicyRefresh`：重算并重写锁；
- `PolicyRefetch`：版本漂移仍失败，但允许在安装阶段补齐缺失构件。

安装计划由锁文件确定性生成；安装器只从本地注册表取内容，逐项“临时目录 → rename”
落盘并写入可核验 marker。安装过程中若上下文取消，本次新建内容全部回滚，不留半成品；
安装后可用 `VerifyInstalled` 复核每个单元是否在位且哈希一致。

## 增量求解

`resolve.Resolver.IncrementalRun` 在上一次 `Snapshot` 与新清单之上工作：

1. 构建新旧两张图，求解新图；
2. 用**结果差异 + 变化边的目标包 + 变化包的可达闭包**精确求出“受影响包集合”；
3. 断言所有**不在**受影响集合内的 lane 与上次选择逐字段相同，否则直接报
   “incremental instability”（增量实现与全量引擎不一致的安全网）；
4. 全部计算成功后才原子写锁；取消或超时发生在提交之前，既有锁文件绝不被改动。

因此增量结论与全量重算保持一致，而实际重算只发生在受影响子图。

## 命令行用法

```bash
# 用本地注册表索引求解并写锁
depresolve resolve   --manifest app.json --index index.json --out dep.lock

# 校验锁与当前清单是否一致
depresolve verify    --manifest app.json --index index.json --lock dep.lock

# 严格按锁安装到本地目录并核验
depresolve install   --index index.json --lock dep.lock --root modules

# 多成员工作区
depresolve workspace --workspace ws.json --index index.json --out dep.lock
```

本地注册表索引示例：

```json
{
  "packages": {
    "example.com/lib": [
      {
        "version": "1.5.0",
        "hash": "sha256:...",
        "deps": [{ "name": "example.com/util", "range": "^1.0.0" }]
      }
    ]
  }
}
```

## 作为库使用

```go
reg, _ := registry.LoadIndexFile("index.json")      // 仅本地数据
r := resolve.New(resolve.Config{Registry: reg, LockPath: "dep.lock"})

m, _ := manifest.LoadFile("app.json")
lockFile, result, err := r.FullRun(ctx, []manifest.Manifest{m})
if err != nil {
    if f, ok := solver.AsFailure(err); ok {
        switch f.Kind {
        case solver.KindConflict: // f.Contradictions 含来源与可用版本
        case solver.KindCycle:    // f.Cycle
        case solver.KindMissingPackage:
        case solver.KindInvalidRange:
        }
    }
    log.Fatal(err)
}
_ = lockFile
_ = result
```
